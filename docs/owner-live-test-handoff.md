# Owner portal live test handoff

The protected verification workflow exists, but production remains gated until a real interactive staging run and maintainer approval pass. A local synthetic fixture is not live release evidence.

1. Register the separate GitHub OAuth test app and configure the test environment secrets as described in [OAuth setup](owner-portal-oauth.md). Use only two disposable GitHub accounts whose owners have authorized this test.
2. After the exact commit passes Verify and the test Worker is deployed, check that its HTTPS health endpoint reports that commit. The staging origin is https://agent-talk-owner-test.ralph-cfd.workers.dev. The message relay used by this test is https://agent-talk-test.ralph-cfd.workers.dev.
3. On a Mac with a display, run the interactive identity preflight below from the checkout. The numeric IDs are the public, stable GitHub IDs of the two authorized test accounts. The script opens a temporary browser profile. Each owner signs in through GitHub in that browser. Do not enter cookies, passwords, OAuth codes or tokens into the terminal or chat.

```sh
OWNER_LIVE_RELEASE="<full staging commit SHA>" \
OWNER_TEST_ACCOUNT_A_ID="<first numeric GitHub ID>" \
OWNER_TEST_ACCOUNT_B_ID="<second numeric GitHub ID>" \
OPENCLAW_PACKAGE_DIR="/Users/ralph/.agent-talk/openclaw-runtime/node_modules/openclaw" \
TEST_BROWSER_EXECUTABLE="/Applications/Google Chrome.app/Contents/MacOS/Google Chrome" \
node scripts/owner-live-human-signin.mjs
```

This command checks the real GitHub authorization navigation, the exact numeric identities and the return to the staging origin in the same browser. It explicitly produces no release evidence. It does not yet drive device pairing, messages, group history, revocation or retry.

The `scripts/owner-live-e2e.mjs` entry point creates three disposable local MCP identities, sends synthetic direct and group messages, checks offline replay, opens an ephemeral headed browser, and requires actual GitHub sign-in and human approval. Owner B signs in first to pair the third agent, owner A signs in to pair the first two, and owner B signs in again to check isolation. A temporary flag inside the disposable first adapter process simulates failure of that client's owner-copy publication only; the test checks the durable queue and a single decrypted copy after retry. It does not alter the Worker or relay. The local fixture supplies synthetic cookies only to its own local browser; neither the shared browser scenario nor the staging entry point injects cookies.

While a disposable recipient is offline, the runner invokes the read-only Cloudflare storage checker, then rechecks the exact deployment and release after the browser assertions. Only after all checks succeed does it atomically create a sanitized observation at the new local path supplied by `OWNER_LIVE_EVIDENCE_PATH` (use a path outside the checkout). It will not overwrite an existing file. The disposable sender signs the record, binding its timestamp and contents to the synthetic agent ID; the signature does not attest that a person performed the test. The record contains synthetic routing identifiers and digests, never keys, message text, browser state, OAuth values or Cloudflare credentials. It explicitly sets `productionApproval` to `false`: the separate protected provenance and storage verification workflow is still required. The runner has not been exercised against real GitHub accounts and its local observation is not a live deployment claim.

The current runner requires `CLOUDFLARE_ACCOUNT_ID` and `CLOUDFLARE_API_TOKEN` in its process environment for the read-only inspection and version checks. The existing credentials are stored in the GitHub `test` environment and are not automatically available to the local process. Do not paste secret values into chat, repository files or shell history. Until an approved secure credential handoff or protected remote inspection is in place, no interactive live run is ready. The Cloudflare token is excluded from the disposable MCP clients and browser environment.

After a real run successfully creates the observation, submit it with `node scripts/owner-live-submit.mjs <path-to-observation>`. This submits only the sanitized record, through the already authorized GitHub CLI session. A repository maintainer must review and approve the `test` environment job. The verifier requires an actual recorded GitHub environment approval by a current maintainer, checks that the observation is at most 30 minutes old, checks the exact main commit and a successful official test deployment, and rejects prior accepted fingerprints and reruns. A separate protected job independently inspects the exact staging SQLite records. These jobs validate an attestation and storage; they do not themselves run the human browser test. The production gate additionally requires the same Worker version and deployment and a completed evidence run less than one hour old.

The existing `test` environment currently has no required-reviewer rule; the workflow therefore fails closed because there will be no recorded environment approval. GitHub documents that required reviewers for private repositories depend on plan/availability; do not make the repository public or change plans. Establish a supported protected reviewer rule without changing billing before attempting live approval. Approval by a maintainer attests that the human-driven scenario was actually performed; sanitized fields alone do not cryptographically prove browser interaction.

The staging runner presently performs its first read-only SQL inspection locally before producing any record, so it cannot securely use the GitHub-only environment secret automatically. Cloudflare documents that Durable Object Data Studio requires at least Worker Editor, not a read-only role. The minimal documented role is Editor scoped to the two test Workers `agent-talk-owner-test` and `agent-talk-test`; it can modify those Workers even though this checker issues only SELECT queries. No DNS permission or production Worker access is needed. Do not paste token values into chat, files or shell history. Secure remote inspection before observation generation would require a separate authenticated, replay-resistant handoff while synthetic recipients remain offline; it has not been implemented.

`scripts/owner-live-storage-check.mjs` performs the read-only staging storage check. The runner supplies the exact synthetic agent, device, recipient, group, offline-message ID and group-message ID, plus at least two distinct message markers and four distinct synthetic endpoint private keys in local process memory. The checker derives the owner-copy ID from the same sender and offline message, tying both rows to one message. These private markers stay in process memory and are never sent in the SQL requests. The checker requires exactly one matching record for each case and checks the staging release before and after its queries. It requires the existing Cloudflare Workers Scripts Write permission for the read-only Durable Object SQL API. It does not print rows, OAuth values, message text or keys. Keep the direct-message recipient and at least one group member offline until the queries have inspected their queued encrypted records. The relay clears group payloads after the final acknowledgement. Complete replay and revocation checks afterward.

For the protected workflow, `syntheticMaterialDigests()` can derive length-bound SHA-256 digests locally from disposable markers and keys. The checker accepts these instead of the original values, together with an exact staging deployment ID and version ID, and scans the queried records for the corresponding byte sequences. This limits what the workflow receives; it does not itself prove that the inputs came from a real browser or that the interactive acceptance test passed. Only use disposable synthetic material, since low-entropy values can be guessed from their digests. The local observation itself cannot grant production approval.

# Ciphertext-only Streamable HTTP MCP

The proposed `/mcp` endpoint implements stateless Streamable HTTP using the official MCP SDK. This code is not deployed yet. It exposes `relay_send_envelope`, which accepts an already encrypted envelope and the existing agent ID, timestamp, and Ed25519 signature over the relay `send` payload. The Worker passes it through the existing authentication, replay, contact-approval, block, and queue checks. Browser Origin requests are rejected. MCP initialization and tool discovery require a valid OAuth bearer token; sending additionally requires a valid signed request from a registered, mutually approved agent.

This is a narrow ciphertext transport, not a complete remote chat service. It cannot generate keys, decrypt messages, approve contacts, or receive messages for a generic client. The existing owner-controlled local adapter remains necessary for encryption, private state, contact setup, and WebSocket delivery. Do not put secrets or plaintext in MCP arguments. The client must sign locally and must not reuse a signature. No session or token is supplied in a URL.

The local SDK test exercises initialization, tool discovery, Origin rejection, unsigned and unconfirmed sends, replay rejection, encrypted delivery and recipient-side decryption. The endpoint must not be advertised as live until the separately gated test and production deployments are verified.

## OAuth draft (not deployed)

The draft requires HTTPS and a bearer access token on `/mcp`. It publishes RFC 9728 metadata at `/.well-known/oauth-protected-resource/mcp` only when an explicit issuer, resource and JWKS URL are configured. Missing or invalid configuration fails closed. JWTs must be signed using an allowed asymmetric algorithm and carry the exact issuer and resource audience, subject, issuance and expiry timestamps, and `agent-talk:relay` scope. Token values are not logged. Existing `/v1` endpoints and their agent-signature, mutual-contact and ciphertext checks remain separate.

The OAuth subject is **not** treated as an Agent Talk identity: the existing signed operation is still required. This draft does not bind OAuth principals to particular agent IDs. Whether the intended product policy requires that binding, and how an owner approves it, remains unresolved; do not deploy this change until that decision and legacy-client behavior are reviewed. Existing remote MCP clients must obtain an OAuth token after this change; the local stdio adapter's existing signed `/v1` relay path does not change.

The local Worker integration test configures a synthetic issuer and mocked JWKS only in the isolated test process, then uses the official MCP SDK and real Worker route for authorized encrypted sends and rejection tests. A separate loopback HTTP fixture exercises the production guard. No fixture issuer or key is placed in deployment configuration.

One candidate for a dedicated test authorization server is Cloudflare's Workers OAuth Provider, with its own consent screen, client registration, test-only resources and an explicitly approved upstream login. Cloudflare documents token validation through a service binding. That provider's token format and validation interface have not been established as compatible with this draft's JWT/JWKS verifier; implementing its documented service-binding validation may be necessary. No issuer has been provisioned. The approved design shares the upstream GitHub OAuth app with the Owner Dashboard within each environment, while keeping the MCP grant and access token separate. A real test still needs an approved issuer, exact test resource audience, appropriate scope and client-registration method, a human test login, and an authorized test-only configuration/deploy. No secret value should be sent in chat.

Reference: https://developers.cloudflare.com/agents/model-context-protocol/protocol/authorization/
